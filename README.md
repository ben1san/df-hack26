# 看護師勤務表 — 師長が書き換えられるルール層

**勤務表を自動で作る製品は既にある。使われないのは「妙に融通が効かない」から。この製品が自動化するのは表ではなく、病棟のルールを病棟自身が育てる経路。**

師長は設定画面を開かない。**過去の表について問いに答える**と最初のルールができ、**毎月の手直しの反復**から次のルールが生まれる。師長は自分の仕事について答えるだけで、設定の語彙は一度も出てこない。

| | |
|---|---|
| Product category | **医療・福祉** |
| 実行基盤 | **Cloud Run**（`asia-northeast1`、1サービス） |
| デプロイURL | `提出前に記入` |
| 中核のGoogle技術 | Cloud Run / **OR-Tools CP-SAT** / Firestore / Vertex AI（Gemini） |

> **提出前に埋める** — ①上のデプロイURL ②`docs/` にアーキテクチャ図（[cloud.google.com/icons](https://cloud.google.com/icons) の公式アイコン）

## 解こうとしている課題

**3交代で深夜勤2名・準夜勤2名を毎日置く12人病棟は、72時間ルールを満たせない。**

【実測】手元のモック病棟の10月の表は法令違反だった。夜勤時間数の総和 975.0h ÷ 夜勤従事者11名 ＝ **月平均88.6時間**（上限72.0h）。師長は毎月これを人力で埋めている。

そして**病棟のルールは製品の設定項目に収まらない。** 先行実装の実データには `新人不算人力`（新人で人員に数えない）`上課`（研修）のような、汎用製品の語彙に無い勤務区分が入っていた。

| 誰の課題か | 何が起きているか |
|---|---|
| 師長 | 自分の病棟のルールを製品の設定項目に翻訳できない。導入研修を受けた師長が交代すると、設定画面は二度と開かれない |
| 病棟 | 法令（72時間ルール）は病棟集計の平均で、しかも分母が解に依存する。**既存のどのDSLでも表現できない**（先行実装のコードを読んで確認した） |

## Google技術を採用した理由

**各要素に代替不可の理由がある。言えない技術は足していない。**

| 選択 | 理由 |
|---|---|
| **Cloud Run** | CP-SATに任意のネイティブ依存が要る。App Engine標準では積めず、GKEとCompute Engineは常時課金でスケールゼロにならない。**求解器がランタイムを決めている**という説明が成り立つ唯一の選択 |
| **1サービスに同梱** | サービス境界を増やすほどデモ中に切れる場所が増える。求解は同期リクエストに収まる（下の実測） |
| **OR-Tools CP-SAT** | Google製（Apache-2.0）。72時間ルールは両辺に分母を掛けると線形になり、`Σ夜勤時間 ≦ 72 × Σ夜勤従事者フラグ` でそのまま通る。**全硬制約を軟にして最小化し、法令由来を重み100で置く**と、師長のルール側が先に破れて実用的な説明文が出る |
| **Firestore** | 保存すべき中心が**追記専用の編集ログ**。同じIDの `create()` 2回目が `AlreadyExists` で落ちるので、**上書きの経路をコードに持たせずに済む**。サーバ側タイムスタンプも要る |
| **Vertex AI**（AI Studioでなく） | ①Cloud Creditが効く ②**APIキーが1本も存在しない**（サービスアカウントのADC） ③課金・ログ・クォータが同一プロジェクトに乗る |

### 捨てた案

| 捨てた | なぜ |
|---|---|
| 最小不充足集合（`sufficient_assumptions_for_infeasibility`） | 12人病棟で**9本中9本を返した**。使えるのは破れ量の側だけだった |
| 公休上限を硬制約で置く | 10秒で `UNKNOWN`。軟制約に落としたら **284msで `OPTIMAL`、しかも破れ0件**。目的関数が探索を導く |
| LLMを初回求解の前に置く | 文章全体から網羅抽出すると、落ちた制約が気づかれないまま最初の1枚に乗る。**指したセル1つ → 制約1本**なら、落ちれば直前の操作が通らないとして即分かる |
| フロントをAngular / Litに | 採点対象のGoogle技術ではあるが、中核の説明にならないと判断してReactを採った（判断: beni） |

## 構成

```text
  ブラウザ（React + Vite + TS / HashRouter）
      │
      ▼
  Cloud Run  asia-northeast1  Python / FastAPI  1コンテナ
      ├ StaticFiles  … Vite のビルド成果物を同じオリジンで配信
      ├ dsl          … 6型。意味境界
      ├ solver       … OR-Tools CP-SAT
      ├ derive       … 段階0の逆算
      └ detect       … 反復検出
      │                    │
      │ ADC（鍵なし）        │
      ▼                    ▼
  Vertex AI Gemini      Firestore
  （翻訳だけ・1箇所）     （追記専用の編集ログ）
```

API と Firestore のコレクション構成は [docs/api.md](docs/api.md)。

## 安全性・拡張性・保守性

**書き換えていい層とだめな層を分けたことが、そのまま安全性の説明になっている。**

1. **書き換え対象をルールだけに限った。** 壊れる層が存在しない
2. **LLMは6型のインスタンス以外を生成できない。** `app/dsl.py` が意味境界で、不正な出力はソルバーに到達しない
3. **破壊的更新が無い。** 荒らされても状態は失われず、`scripts/fixture.py` と `seed/` から巻き戻せる
4. **鍵が1本も存在しない。** ADC認証で、公開リポジトリに秘密情報を置く経路がそもそも無い。Firestoreのsecurity rulesは **deny all**（ブラウザはFirestoreを直接触らない）

**拡張の方向も1箇所に閉じてある。** 保存層は `REPO` 環境変数1本で `JsonRepo`（GCP不要）と `FirestoreRepo` が入れ替わり、**両者でアプリの返す値が完全に一致する**ことを実測で確認している（下記）。

## 実測

【実測】2026-11-09、12人病棟・30日・ルール10〜11本。

| | |
|---|---|
| 夜勤段の求解 | `OPTIMAL` **284〜429ms** |
| 日勤段の求解 | `OPTIMAL` **63〜81ms** |
| 不充足の判定＋破れ量 | **68〜82ms** |
| Dockerイメージ（OR-Tools込み） | **155MB** |
| フロントのバンドル | 298kB / gzip **94kB** |
| 本物のFirestore（`asia-northeast1`）1操作 | **37〜52ms**（エミュレータは1〜3.5ms） |

【実測】保存層を本物のFirestoreに差し替えても、アプリの返す値は `JsonRepo` と**完全に一致した**（ルール10本・反復検出8件・鍵の数 K=308・棄却0件）。差はレイテンシだけで、1操作あたり一律 +35〜50ms。再現は `scripts/bench_repo.py` と `scripts/verify_firestore.py`。

【推論】この固定費は往復1回ぶんであって操作の重さではないので、**Cloud Run を Firestore と同じ `asia-northeast1` に置くことが前提条件。**

## デモの歩き方

```bash
uv venv --python 3.12 && uv pip install -e .
uvicorn app.main:app --port 8077 &          # REPO 未指定なら data/ にJSONで保存（GCP不要）
cd frontend && npm install && npm run build && cd ..
python scripts/fixture.py                   # 8月から使っている状態を作る
# → http://localhost:8077/#/roster
```

`fixture.py` が作り物にしているのは**師長の振る舞いの脚本だけ**。各月の提案はその月のルールで実際にCP-SATが解いた出力で、編集はその提案に対する実際の差分。

反復検出は編集ログの上にしか見えず、履歴はこの製品を使い始めてからしか貯まらない。そのため「この病棟は8月から使っている」状態を作ってから見せる。

## 層

| 置き場所 | 何が居るか |
|---|---|
| `app/dsl.py` | 6型。**意味境界。** LLMもUIも病院設定も、ここを通らずに求解器へ届かない |
| `app/derive.py` | 段階0。過去の表を数えて候補を出す。**作りはしない** |
| `app/detect.py` | 反復検出。鍵の一致と、観測量から決まる閾値 |
| `solver/cpsat.py` | CP-SAT。表の生成と、不充足原因＋破れ量 |
| `app/translate.py` | Gemini。**LLMが出る唯一の場所。**求解には関与しない |
| `app/repo.py` | 保存層。JSON実装とFirestore実装を環境変数1本で差し替え |
| `app/main.py` | API。**表を上書きするエンドポイントが無い** |
| `frontend/src/lib/types.ts` | `dsl.py` の写し。型が境界をまたぐ |
| `frontend/src/screens/` | 7画面。HashRouter なので再読み込みが壊れない |
| `scripts/` | 検証と再現。`fixture.py`（デモ状態）`bench_repo.py`（保存層のレイテンシ）`verify_firestore.py`（追記専用などの性質）`smoke_vertex.py`（LLM経路）`deploy.sh` |

## 構成上の禁止

後から入れ直すと作り直しになるので、先に手を付けた。

- **表を保存するAPIを作らない。** 表は状態ではなく（提案 ＋ 編集ログ）の射影。1本でも上書きを許すと差分が消え、反復が観測できなくなる
- **提案と現状を別に持つ。** 1本の配列で持つと「棄却」が定義できない
- **全規則にインスタンス単位の強制リテラルを付ける。** 後から全規則に付け直すのは実質作り直し
- **ブラウザはFirestoreを直接触らない。** security rulesはdeny all。**APIキーは存在しない**
- **LLMを初回求解の前に置かない。**
- **段階0は「ルールにしますか」と聞かない。** 成立回数が100%なら可否、例外があれば境界値、人に紐づくなら期限。**候補ごとに問いの形が違う**
- **法令由来は逆算しない。** 表から数えるものではないので、病棟登録のときに投入する（`app/main.py` の `_law_rules`）
- **閾値を固定値にしない。** 鍵の数 K と1ヶ月あたりの手修正から毎月計算する
- **一度答えた反復は、もう聞かない。**
